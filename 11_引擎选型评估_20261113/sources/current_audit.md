## 2. 为什么继续加“模式”不能自然变成通用引擎

1. **输入主要是配方，不是场景。** 配置没有通用 `entities[] / components[] / parent / transform / collider / material / behavior` 对象模型。新玩法目前要同时改模式枚举、配置校验、模拟分支、预设、界面字段，往往还要加渲染专用分支。证据：[config.py](D:/codex/AGI/AI视频三项目评估_20261111/06_本地部署/relaxing-physics/src/data/config.py:25)、[UI字段表](D:/codex/AGI/AI视频三项目评估_20261111/06_本地部署/relaxing-physics/src/ui/app.js:19)、[渲染分支](D:/codex/AGI/AI视频三项目评估_20261111/06_本地部署/relaxing-physics/src/rendering/renderer.py:440)。
2. **几何布局写在代码。** 基础圆环中心、半径固定在 [simulation.py](D:/codex/AGI/AI视频三项目评估_20261111/06_本地部署/relaxing-physics/src/core/simulation.py:15)；双通道边界固定在 [versus.py](D:/codex/AGI/AI视频三项目评估_20261111/06_本地部署/relaxing-physics/src/core/versus.py:30)。多米诺和玻璃确实有矩形刚体，但其布局和额外轨迹通过专属元数据传递，见 [stack_domino.py](D:/codex/AGI/AI视频三项目评估_20261111/06_本地部署/relaxing-physics/src/core/stack_domino.py:354)，不是一个可拖放的通用物体列表。
3. **轨迹明确限定二维。** [scene.py](D:/codex/AGI/AI视频三项目评估_20261111/06_本地部署/relaxing-physics/src/data/scene.py:64) 校验位置数组必须为 `[采样数,槽位数,2]`。它没有通用每物体三维旋转、缩放、相机、光源、网格/材质引用。把最后一维改成3不能自动补齐这些概念，也会影响现有读取器、缓存和测试。
4. **Pillow 是二维绘图层。** [renderer.py](D:/codex/AGI/AI视频三项目评估_20261111/06_本地部署/relaxing-physics/src/rendering/renderer.py:13) 固定逻辑画布720×1280，以 ImageDraw 绘制不同玩法。已有光晕、变浅和阴影可以做平面风格，不能提供真实三维透视、遮挡、PBR 材质、灯光与反射。
5. **界面是表单，不是场景编辑器。** [app.js](D:/codex/AGI/AI视频三项目评估_20261111/06_本地部署/relaxing-physics/src/ui/app.js:133) 和 [index.html](D:/codex/AGI/AI视频三项目评估_20261111/06_本地部署/relaxing-physics/src/ui/index.html:15) 没有场景树、画面拾取/拖放、旋转缩放手柄、编组/对齐/吸附、复制物体、撤销重做、资源浏览器、关键帧轨道或碰撞规则图。播放滑杆只是跳到已算好的时间，不是动画编辑时间线。
6. **没有通用实时调试面板。** 现有回归测试与日志很有用，但工作台不显示当前接触对、法线/冲量、碰撞体轮廓、为什么该球未分裂、逐物理步执行或物体检查器。近期碰撞问题说明这些调试功能应进入新工程的首版范围。

现有 UI/配置只开放四档9:16尺寸和24/25/30/50/60fps，见 [config.py](D:/codex/AGI/AI视频三项目评估_20261111/06_本地部署/relaxing-physics/src/data/config.py:25)。底层编码器有更宽的参数范围，不等于现有工作台已支持任意宽高、横屏或4K。

当前 `frame_at()` 使用最近的较早采样帧，没有位置插值，见 [scene.py](D:/codex/AGI/AI视频三项目评估_20261111/06_本地部署/relaxing-physics/src/data/scene.py:172)。把30Hz数据导出为60fps会重复采样帧；“可选60fps”不自动等于每秒60份不同运动状态。现有确定性回归比较了同种子的判定时刻与胜负，见 [test_versus_scheme.py](D:/codex/AGI/AI视频三项目评估_20261111/06_本地部署/relaxing-physics/tests/test_versus_scheme.py:94)，不构成跨机器/跨版本/换引擎后逐位一致的保证。保留已烘焙轨迹再渲染，才是保住某条成片赛果的直接方式。

| 浏览器参数表单与PNG播放 | 可保留过渡界面 | 通用场景编辑器、GPU视口与可视调试多数需另建 |

不建议使用“旧代码可以复用80%”这类没有分母的说法。可以明确复用的是规则、测试情景、内容资产和导出经验；承担新目标的编辑器、3D场景数据、渲染与物理接入是另一块工程。

## 4. 2.5D 的两种实现必须分清

- **二维物理＋三维显示**：保留 Pymunk/旧轨迹，把圆显示为球、线段显示为挤出的几何体，锁在一个运动平面上，用正交相机、灯光和阴影拍摄。适合尽快给已有玩法升级质感；可以保持同一份二维运动结果。遮挡关系和视觉厚度要设计好，避免画面像碰到、实际2D碰撞体没接触。
- **三维物理＋受限运动或正交相机**：在 Godot/其他3D引擎里约束轴向，做出2.5D画面。具备真实厚度和三维接触，但它是另一套物理模拟，旧 Pymunk 赛果不能原样继承。

新工程最好允许明确选择 `2D physics / 3D physics`。2.5D 是显示与约束方式，不应悄悄混用两个求解器同时控制同一个物体。

## 6. 对主方案选择的建议

如果用户以后仍主要调整已写好的六种二维玩法，增量升级最直接。如果明确要长期做任意布置、2D/2.5D/3D、多种机制自由组合，宜使用成熟引擎的场景、渲染、物理和编辑器基础，开发解压视频专用插件/工作流，同时保留当前项目作2D参考后端与回归基线。

“重新实现产品工作台”与“从零写物理求解器、渲染器和编辑器”不是一回事。前者可以用 Godot 或 Web 开源引擎实现专用产品，后者会把大量精力用在与短视频创作无关的底层维护上。现有资产不需要删除，是否迁移也不应以强行保留全部旧源代码为目标。

首版优先验收同一个场景的完整闭环：拖进一个球、几面墙和文字 → 选择碰撞分裂/变色 → 实时运行并单步查接触 → 固定种子烘焙 → 改字体/材质后重渲染 → 导出1080×1920/60fps视频。2D与3D各用一个代表场景验证后，再扩大功能清单。
